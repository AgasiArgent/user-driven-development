# Набор для вайбкодера: «пользователи — тестировщики»

**Дата:** 2026-10-17 · **Статус:** на ревью у владельца · **Ветка:** `vibecoder-kit` (локально, не отправлена)

## 1. Зачем

Сейчас репозиторий написан для инженера: пакеты виджета, доставки и полной версии на TypeScript, двенадцать принципов, демо на Next.js. Вайбкодер — человек, который делает приложение руками агентов и не считает себя инженером, — такое руками не соберёт.

Цель — набор, который вайбкодер вставляет в своё приложение одной фразой своему агенту, после чего:
- пользователи сообщают о проблемах кликом по сломанному месту;
- агенты исследуют жалобу и чинят её после одобрения человека;
- исправление проверяется на живом сайте, и автор жалобы видит статус;
- раз в неделю человек отвечает на накопившиеся продуктовые вопросы, а агент доделывает остальное;
- рутины раз в неделю убирают мёртвый код, дубли и ищут уязвимости.

Подача объединяет три угла: плейбук из правил, идею «пользователи — тестировщики» и честные цифры из рабочей системы.

### Критерии успеха

1. Свежий агент, получивший только фразу из README, ставит набор в чистое приложение на Next.js + Supabase и в приложение на Vite + React + Express, и сквозной прогон проходит в обоих (раздел 9).
2. Весь набор работает на подписке Claude Pro или Max без API-ключа.
3. README понятен человеку, который не читал остальной репозиторий: что это, для кого, одна фраза, что получишь, сколько стоит.
4. После публикации — звёзды и форки, и хотя бы несколько человек, подключивших набор и рассказавших, что сломалось.

### Вне рамок

- Мобильные приложения.
- Трекеры кроме GitHub Issues в наборе по умолчанию (Linear остаётся в продвинутой части).
- Перенос существующего кода (`widget/`, `delivery/`, `demo/`, `full/`) по папкам.
- Готовые npm-пакеты для установки командой.

## 3. Путь вайбкодера

1. Открывает README, копирует фразу:
   > Read https://github.com/AgasiArgent/user-driven-development/blob/main/SETUP.md and set it up in this app.
2. Агент читает `SETUP.md`, задаёт вопросы (раздел 5.1) и подключает набор.
3. В приложении появляется кнопка «Report a problem». Пользователь кликает по сломанному месту и пишет, что не так.
4. На GitHub появляется issue с меткой `feedback`, агент оставляет комментарий с исследованием.
5. Вайбкодер читает issue и ставит метку `approved`.
6. Агент открывает черновой PR: тест, который падает на старом коде, и исправление.
7. Вайбкодер сливает и деплоит. Тот же тест проходит против живого сайта, issue закрывается, пользователь видит «проверено».
8. Раз в неделю вайбкодер пишет агенту «run WEEKLY.md».
9. Раз в неделю рутины открывают черновые PR или issue.

## 5. Цикл обработки жалобы

### 5.1. Что агент спрашивает при установке

1. Репозиторий GitHub (обычно определяется из `git remote`).
2. Есть ли база данных и какая (Supabase, Postgres, нет).
3. Где хранить скриншоты (хранилище приложения за логином; по умолчанию — то же, что у приложения).
4. Есть ли в проде тестовый аккаунт для проверки (если нет — проверка в проде выключена, остальное работает).
5. Как деплоится приложение (Vercel, Netlify, другое) — от этого зависит запуск `udd-verify.yml`.
6. Репозиторий публичный или приватный — от этого зависит рутина безопасности (раздел 7.3).

Агент сам создаёт метки и проверяет секреты (`gh label create`, `gh secret list`). Секреты (`CLAUDE_CODE_OAUTH_TOKEN`, токен GitHub для приложения, данные тестового аккаунта) вводит человек; агент говорит, какие и где взять, и не печатает их значения.

### 5.2. Приём жалоб в приложении

- **Виджет** — по образцу `widget/src`: текст, скриншот, CSS-селектор, адрес страницы, ошибки консоли, упавшие запросы, маскировка полей ввода (`mask.ts`).
- **`POST /api/feedback`** (имя маршрута подстраивается под стек):
  - только для вошедшего пользователя; ограничение частоты;
  - запись в таблицу `feedback_reports` (статус `received`); скриншот — в хранилище за логином;
  - сразу создаёт issue с меткой `feedback`, токен GitHub только на сервере, право — только issue;
  - тело issue строится по правилам `delivery/src/issueBody.ts`: HTML экранируется, после каждого `@` — пробел нулевой ширины;
  - при ошибке GitHub запись остаётся `received` и досылается при следующем запросе к маршруту или к странице «Мои жалобы».
- **Без базы данных:** issue создаётся напрямую, агент предупреждает, что жалоба может потеряться при сбое GitHub.
- **Страница «My feedback»:** жалобы пользователя и их статусы; статус читается из меток issue при открытии страницы.

### 5.3. Метки и статусы

| Метка | Ставит | Статус для пользователя |
|---|---|---|
| `feedback` | маршрут приёма | Received |
| `researched` | `udd-research.yml` | Looked into |
| `approved` | человек | Approved |
| `in-progress` | `udd-fix.yml` (остаётся и после открытия PR, пока не проверено превью) | In progress |
| `fix-ready` | `udd-preview.yml`, когда тест прошёл на превью | Fix ready |
| `shipped` | `udd-fix.yml` (задача shipped) при слиянии PR | Shipped |
| `verified` | `udd-verify.yml` | Verified in production |
| `needs-human` | `udd-fix.yml`, `udd-preview.yml`, `udd-verify.yml` | Waiting for the developer |
| закрыт как not planned | человек | Declined |

### 5.4. Workflow

Все на `anthropics/claude-code-action` с `claude_code_oauth_token`. Подтверждено документацией Action (`docs/setup.md`): токен подписки Pro и Max подходит. Каждый запуск расходует лимиты подписки.

**`udd-research.yml`** — при появлении issue с меткой `feedback`.
- Агент читает код, ищет вероятную причину, сравнивает с открытыми issue на дубли, пишет, в чём не уверен, и описывает тест, который должен упасть.
- Права: чтение кода и комментарий в issue; без записи в репозиторий, без shell.
- Текст жалобы — недоверенный ввод. В комментарий агента не попадают упоминания (`@`) и слова-триггеры других агентов: вывод проходит тот же фильтр, что и тело issue.
- Ставит `researched`.

**`udd-fix.yml`** — человек (не бот) поставил `approved` на issue с `feedback`. Идея «red on production, green on preview»: тест красный на живом сайте и зелёный на превью. Задачи (имена как в файле):
- `guard` (`issues: write`): тот же отбор, что и раньше (`sender.type == 'User'`, метка `feedback`, `vars.UDD_AGENT_ENABLED == 'true'`, один запуск на issue); ставит `in-progress`.
- `agent-1`, `agent-2`, `agent-3`: держат токен модели (`CLAUDE_CODE_OAUTH_TOKEN` или `ANTHROPIC_API_KEY`), права `contents: read`, без установки, без тестов, без запуска кода проекта. Агент пишет ОДИН Playwright-тест с пометкой `@udd-<номер issue>` и исправление. Перед агентом сохраняется `.git/config`, перед `git add` он восстанавливается, а `.git/hooks` удаляется. Патч уходит артефактом, его sha256 — выход задачи. Попытки 2 и 3 идут только если предыдущая проверка red упала, на свежем раннере, и получают прошлую причину в промпте.
- `red-1`, `red-2`, `red-3`: без токена модели и без токена на запись (`contents: read`, `persist-credentials: false`, без кэша). Берут базовый коммит, проверяют sha256 патча, применяют ТОЛЬКО файлы патча, подходящие под `vars.UDD_TEST_GLOB` (конфиг Playwright, tsconfig и global setup закрыты списком запретных путей), ставят зависимости и запускают `${UDD_E2E_CMD} --grep` с границей тега против `vars.UDD_PROD_URL` под `UDD_TEST_USER_EMAIL` и `UDD_TEST_USER_PASSWORD`. Результат — `base.json`. Вердикт здесь не считается.
- `verdict-1`, `verdict-2`, `verdict-3`: читают `base.json` доверенным `red-first.mjs` только чтобы решить, нужна ли следующая попытка.
- `publish` (`contents: write`, `pull-requests: write`, `issues: write`; код проекта не запускает): до применения патча копирует `red-first.mjs`, `no-fly-check.mjs` и `no-fly.txt` с базового коммита в `$RUNNER_TEMP/trusted`. Проверяет sha256, считает `baseVerdict` по каждому `base.json`, берёт первую попытку с красным тестом, применяет её патч, проверяет запретные пути (`git diff --cached --name-only -z --no-renames`, затем `no-fly-check.mjs -z`), пушит ветку `udd/fix-<n>` и открывает ЧЕРНОВОЙ PR «Fixes #<n>». Метка остаётся `in-progress`: превью ещё не проверено. Если красных попыток нет — комментарий с тремя причинами, `needs-human`, `in-progress` снимается.
- `shipped`: при слиянии PR из ветки `udd/fix-<n>` этого репозитория ставит `shipped`, снимает `fix-ready` и `in-progress`.
- Граница тега везде одна — `tagRegex(tag)` из `red-first.mjs` (`@udd-1(?![0-9])`).

**`udd-preview.yml`** — событие `deployment_status` (успех, окружение не production) или ручной запуск (`workflow_dispatch`, поля `url` и `issue`). Модель не участвует.
- `find` находит PR по sha деплоя (`commits/<sha>/pulls`); подходят только ветки `^udd/fix-[0-9]+$` этого же репозитория.
- `test` — единственная задача с кодом проекта: чекаут головы PR, установка, запуск помеченного теста против `environment_url` деплоя (запасной вариант — `target_url`) под тестовым аккаунтом. Секрет `UDD_PREVIEW_BYPASS` (необязательный, защита развёртываний Vercel) приходит в тест переменной окружения; конфиг Playwright отправляет его заголовком `x-vercel-protection-bypass`. Токена на запись нет.
- `verdict` (`issues: write`, код проекта не запускает, скрипты с ветки по умолчанию): `red-first.mjs head`. Тест прошёл — `fix-ready`, `in-progress` снимается, комментарий. Нет — `needs-human`, комментарий с причиной и ссылкой на прогон.
- Vercel создаёт события деплоя в GitHub сам. Для других хостингов владелец запускает workflow вручную с адресом превью.

**`udd-verify.yml`** — событие `deployment_status` со статусом `success` в окружении production (Vercel и Netlify отправляют его в GitHub), плюс ручной запуск с адресом.
- Для каждого issue с `shipped` без `verified` запускает тесты `@udd-<номер>` (граница тега) против `UDD_PROD_URL` под тестовым аккаунтом. Тесты идут в задаче без токена на запись, метки меняет отдельная задача скриптами с ветки по умолчанию.
- Прошёл — `verified`, комментарий, issue закрыт. Упал — `needs-human`, комментарий со ссылкой на прогон.
- Принятый риск: тесты пишет агент, и они идут против продакшена и превью под тестовым аккаунтом. Они не должны менять настоящие данные; `CLAUDE.md.snippet` требует, чтобы агент писал тесты, работающие только с данными тестового аккаунта.

## 6. `WEEKLY.md`

Запускается локально в Claude Code: «run WEEKLY.md». Шаги:
1. Собрать застрявшее: `needs-human`; `approved` без PR дольше 3 дней; PR с красными проверками; исследования с открытыми вопросами; PR рутин без ревью.
2. Сгруппировать по продуктовым вопросам; задать все сразу, к каждому — рекомендуемый ответ.
3. Реализовать то, на что есть ответ: падающий тест, исправление, черновой PR, метки как в цикле.
4. Для публичного репозитория — проверка безопасности (раздел 7.3), находки только в терминале.
5. Отчёт: жалоб пришло / исправлено / проверено в проде / возвращено на доработку за неделю; что ждёт человека.

## 7. Рутины

### 7.1. Механика

`templates/workflows/udd-routine.yml`: расписание раз в неделю + ручной запуск, матрица по рутинам. Каждая рутина — промпт из `templates/routines/<name>.md`, запуск через Claude Code Action по подписке. Результат — черновой PR с меткой `routine` (мёртвый код, дубли) или issue (безопасность).

### 7.2. Правила рутин

1. Не больше одного открытого PR или issue на рутину: если предыдущий не закрыт, запуск пропускается.
2. Отклонённая находка записывается в `.udd/known-findings.json` и больше не предлагается.
3. Изменения проходят тесты проекта и проверку запретных путей.
4. Находки приходят туда, где их видят: в PR или issue, а не в артефакт сборки.
5. Успех рутины меряется влитыми PR и закрытыми issue, а не запусками; `WEEKLY.md` показывает это в отчёте.

### 7.3. Рутина безопасности

Проверяет весь код раз в неделю по списку:

| Проверка | Пример находки |
|---|---|
| Каждый серверный маршрут проверяет вход | Эндпоинт отдаёт данные без логина |
| Пользователь видит только свои данные | Чужая запись открывается подстановкой id; у таблицы Supabase выключен RLS |
| Секретные ключи не попадают в браузер | Ключ OpenAI или `service_role` в переменной `NEXT_PUBLIC_*` |
| Текст пользователя не вставляется как HTML | `dangerouslySetInnerHTML` / `v-html` с данными из базы |
| Нет склеивания SQL из ввода | Сырой запрос со строкой из формы |
| Зависимости без известных уязвимостей | `npm audit`; обновление в пределах совместимых версий |
| В git нет секретов | Токен в закоммиченном `.env` |

Правила:
- **Сначала находка, исправление — только после `approved`.** Никогда одним шагом.
- **Секрет в git** — issue «rotate this key», не PR.
- **Приватный репозиторий:** рутина по расписанию, находки — issue с меткой `security`.
- **Публичный репозиторий:** рутина по расписанию выключена; проверка входит в `WEEKLY.md` и запускается локально, находки только в терминале; исправление — обычным коммитом без описания уязвимости. Если на этапе плана подтвердится, что токен workflow может создавать черновики security advisory, публичный вариант переходит на них.
- Платная проверка PR через `anthropics/claude-code-security-review` (только API-ключ, только изменения в PR) упоминается в `ROUTINES.md` как дополнение.

## 8. Тексты

### 8.1. README

1. «Make your users your testers.» Для кого: один человек или маленькая команда, которые делают приложение агентами и у которых есть пользователи.
2. Фраза для вставки агенту.
3. Что получаешь: схема цикла, еженедельный запуск, три рутины.
4. Цифры из рабочей системы (раздел 10).
5. Короткий список правил → `RULES.md`.
6. Стоимость: подписка Claude Pro или Max; для приватных репозиториев — минуты GitHub Actions (уточнить лимит на этапе плана).
7. «Try it first»: демо и `docker compose up`.
8. «Advanced: how I run it in production»: полная версия, история проекта, модель угроз.
9. Contributing.

Язык — английский, стиль — простой, без маркетинговых слов; прогон через навык `humanizer`.

### 8.2. `RULES.md`

Двенадцать правил из `docs/concept.md`, переписанные для вайбкодера, плюс правила рутин (7.2) и безопасности (7.3) — сжато до трёх новых. Формат каждого:
- **Rule** — одна фраза;
- **Why** — какая поломка в рабочей системе к нему привела, с цифрой, если она проверена; истории про рутины не используются;
- **Enforced by** — файл или workflow набора.

### 8.3. Пост

Пишется после приёмки (раздел 9). Угол: «Make your users your testers: an open-source kit you paste into Claude Code». Внутри: кто автор одной строкой, идея, цифры, 3–4 правила, фраза для вставки, ссылка. Первая площадка — r/ClaudeCode (флейр «Built with Claude Code»).

## 9. Приёмка

Без неё набор не публикуется.

1. **Два чистых приложения** в одноразовых репозиториях: Next.js + Supabase и Vite + React + Express. Свежая сессия Claude Code получает только фразу из README.
2. **Сквозной прогон в каждом:** жалоба через виджет → issue → комментарий исследования → `approved` → черновой PR, где тест падает на продакшене → превью-деплой ветки → `udd-preview.yml`: тест проходит, `fix-ready` → слияние → деплой → `udd-verify.yml` → `verified` на странице «My feedback».
3. **Рутины:** ручной запуск каждой; рутина безопасности находит заранее посаженную дыру (таблица без RLS или ключ в `NEXT_PUBLIC_*`).
4. **Статические проверки:** `actionlint` на все шаблоны; существующие тесты репозитория зелёные; проверка обезличивания перед отправкой.
5. **Отказы:** GitHub недоступен при отправке жалобы (жалоба досылается); метку `approved` ставит бот (fix не запускается); тест не падает на продакшене (попытка не засчитана); тест не проходит на превью (`needs-human`).

Одноразовые репозитории на аккаунте владельца и любое развёртывание, которое может стоить денег, — только с его согласия на этапе плана.
